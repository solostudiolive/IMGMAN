<objective>
## Goal
Make star ratings (1–5) editable from the inspector and persist them to the library DB.
Clicking a star sets the rating; clicking the current rating clears it to 0. This
completes the MVP "star ratings (1–5)" requirement and stands up the reusable
`items:update` mutation that tags, folders, notes, and search-by-rating will reuse.

## Purpose
Phase 4 is "Organize & search" — the first organizing primitive is rating an asset.
Ratings are already shown read-only in the inspector (Phase 3); this plan adds the write
path. Equally important, it establishes the item-mutation pattern (validated `items:update`
IPC + optimistic inspector update) so later Phase 4 slices don't each reinvent it.

## Output
- `items:update(id, patch)` IPC + `updateItem` service (rating only for now, clamped 0–5).
- Interactive star-rating control in the inspector, persisting on click.
- `ItemPatch` type shared via preload/types.
</objective>

<acceptance_criteria>

## AC-1: Setting a rating from the inspector
```gherkin
Given an item is selected and shown in the inspector
When the user clicks the Nth star (N in 1..5)
Then the item's rating becomes N
And the inspector shows N filled stars immediately
And the new rating is written to the items table
```

## AC-2: Clearing a rating
```gherkin
Given the selected item has rating N
When the user clicks the Nth (currently-highest filled) star again
Then the rating resets to 0 (no stars filled)
And 0 is persisted
```

## AC-3: Ratings persist
```gherkin
Given the user set a rating on an item
When they select another item and reselect the first (or relaunch the app)
Then the inspector shows the previously-set rating (read from the DB, not just local state)
```

## AC-4: items:update is validated and safe
```gherkin
Given the renderer calls items.update(id, { rating })
When rating is outside 0..5 or not an integer
Then the value is clamped/rounded into 0..5 before the DB write
And when id is unknown or no library is open
Then the call is a safe no-op returning null (no throw across IPC)
```

</acceptance_criteria>

    Stand up the reusable item-mutation path; scope the patch to `rating` for this plan.

    - In `src/main/services/items.ts`: add `export interface ItemPatch { rating?: number }`.
      Add `updateItem(id: string, patch: ItemPatch): FullItem | null`:
        - Return null if `!isDatabaseOpen()`.
        - Build the SET clause only from provided keys. For `rating`, clamp+round:
          `Math.max(0, Math.min(5, Math.round(rating)))`.
        - If no recognized keys are present, skip the UPDATE (still return the current row).
        - Run `UPDATE items SET rating = ? WHERE id = ?` (parameterized), then return
          `getItem(id)` so callers get the canonical persisted row (null if id unknown).
      Keep it shaped so future fields (note, etc.) slot into ItemPatch + the SET builder.
    - In `src/main/ipc/items.ts`: register
      `ipcMain.handle('items:update', (_e, id: string, patch: ItemPatch) => updateItem(id, patch))`.
      Import `updateItem` + `ItemPatch`.
    - In `src/preload/index.ts`: add `update: (id, patch) => ipcRenderer.invoke('items:update', id, patch)`
      to the `items` namespace.
    - In `src/preload/types.ts`: add `ItemPatch` (mirror) and
      `update: (id: string, patch: ItemPatch) => Promise<FullItem | null>` to `IpcApi.items`.
    Avoid: string-interpolating column names; accepting arbitrary keys (only allow-listed
    fields reach SQL); throwing across IPC for unknown ids (return null).
