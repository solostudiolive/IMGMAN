<objective>
## Goal
Add many-to-many tags: assign and remove tags on the selected item from the inspector,
creating tags on the fly. Tags are stored in the existing `tags` / `item_tags` tables and
de-duplicated by name. An autocomplete of existing tag names speeds reuse.

## Purpose
Tags are the core organizing primitive of the MVP ("tags (many-to-many)") and the main
axis the search phase (04-04) will filter on. This plan delivers the tag data layer +
IPC and the inspector tag editor, reusing the optimistic-edit pattern from 04-01.

## Output
- `tags` service (list all, list for item, add by name, remove) over `tags`/`item_tags`.
- `tags:*` IPC + `Tag` type shared via preload/types.
- `TagEditor` component (chips with remove + add input with datalist) wired into the inspector.
</objective>

<acceptance_criteria>

## AC-1: Add a tag to an item
```gherkin
Given an item is selected in the inspector
When the user types a tag name and confirms (Enter)
Then a chip for that tag appears on the item
And the tag is persisted in tags (created if new) and linked in item_tags
And re-selecting the item later still shows the tag (read from the DB)
```

## AC-2: Tags are de-duplicated by name
```gherkin
Given a tag "design" already exists (on this or another item)
When the user adds "design" (any surrounding whitespace, same casing) to an item
Then the existing tag row is reused (no duplicate tags row)
And adding a tag the item already has is a no-op (no duplicate chip)
```

## AC-3: Remove a tag from an item
```gherkin
Given the selected item has a tag chip
When the user clicks the chip's remove (×) control
Then the chip disappears and the item_tags link is deleted
And the tag itself remains available for other items (tags row not deleted)
```

## AC-4: Existing tags are suggested
```gherkin
Given tags exist in the library
When the user focuses the add-tag input
Then existing tag names are offered as autocomplete suggestions (datalist)
```

## AC-5: tags IPC is validated and safe
```gherkin
Given the renderer calls a tags:* channel
When the tag name is empty/whitespace-only
Then add is a no-op (no blank tag created)
And when no library is open or the item id is unknown
Then calls return an empty list / no-op without throwing across IPC
```

  <action>
    Create `src/main/services/tags.ts` (mirror items.ts: guard on isDatabaseOpen, prepared
    statements, randomUUID for ids). Define `export interface Tag { id: string; name: string;
    color: string | null }`. Functions:
      - `listAllTags(): Tag[]` — all tags ordered by name (empty when no library).
      - `listTagsForItem(itemId): Tag[]` — JOIN item_tags→tags for itemId, ordered by name.
      - `addTagToItem(itemId, name): Tag[]` — trim name; if empty, return current tags
        (no-op). Find existing tag by exact name; if none, INSERT a new tags row
        (id = randomUUID(), color = null). INSERT OR IGNORE into item_tags(item_id, tag_id)
        so a repeat link is a no-op. Return `listTagsForItem(itemId)`.
      - `removeTagFromItem(itemId, tagId): Tag[]` — DELETE FROM item_tags WHERE item_id=? AND
        tag_id=? (leave the tags row intact). Return `listTagsForItem(itemId)`.
    Use a transaction in addTagToItem (lookup-or-insert + link) for consistency.
    Create `src/main/ipc/tags.ts` with `registerTagsIpc()` registering:
      `tags:listAll` → listAllTags(); `tags:listForItem` → (id) listTagsForItem(id);
      `tags:add` → (id,name) addTagToItem(id,name); `tags:remove` → (id,tagId)
      removeTagFromItem(id,tagId). Call `registerTagsIpc()` from `src/main/ipc/index.ts`.
    Extend preload `window.api` with a `tags` namespace (listAll/listForItem/add/remove) and
    add the matching `Tag` type + `tags` block to `IpcApi` in `src/preload/types.ts`.
    Avoid: interpolating values into SQL (use bound params); deleting tags rows on unlink;
    creating blank/whitespace tags; throwing across IPC for unknown ids (return []/no-op).
  </action>
