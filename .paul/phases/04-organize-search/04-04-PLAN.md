<objective>
## Goal
Add keyword search + filters: a search bar over item name / note / tag names, combined with
filters for type, format (ext), minimum rating, and import-date range. Results replace the
grid contents. Search uses parameterized LIKE queries (no FTS wiring this plan).

## Purpose
Search is the last MVP organizing capability ("keyword search + filter by format/type/rating/
date"). It closes Phase 4 and the collect → organize → search → browse loop, making the
library usable at scale by letting the user find assets instead of scrolling.

## Output
- `search` service: one parameterized query over items (name/note/tag LIKE + type/ext/rating/
  date filters), returning the grid Item projection.
- `items:search(criteria)` IPC + a shared `SearchCriteria` type via preload/types.
- `SearchBar` (text + type checkboxes + format + min-rating + date range + clear) wired into
  LibraryGate as a third grid "scope" (search overrides the folder filter).

## Decision (resolved at plan time)
LIKE-based search, NOT FTS5. Rationale: FTS5 indexes only name/note (tags need a separate
match either way), items_fts is currently unpopulated/untriggered, and LIKE over name/note +
a tag-name subquery is a single consistent path that covers tags and stays well under the
<0.5s @ 50k target at local-SQLite scale. Properly wiring items_fts (triggers + backfill) is
deferred to a V1 perf pass.
</objective>

<acceptance_criteria>

## AC-1: Keyword search by name
```gherkin
Given items exist in the library
When the user types text in the search bar
Then the grid shows only items whose name contains that text (case-insensitive)
And clearing the search restores the prior view
```

## AC-2: Search also matches note and tag names
```gherkin
Given an item has a note and/or a tag whose text contains the query
When the user searches for that text
Then the item appears in the results (name, note, OR tag-name match)
```

## AC-3: Filter by type and format, combined with the query
```gherkin
Given a query and one or more type checkboxes (e.g. image) are active
When the search runs
Then results match the query AND are of a selected type
And when a format (ext, e.g. "png") is also given, results additionally match that ext
And multiple selected types are OR'd among themselves, then AND'd with the rest
```

## AC-4: Filter by minimum rating and import-date range
```gherkin
Given a minimum rating (e.g. 3+) and/or a from/to date are set
When the search runs
Then results include only items with rating >= the minimum
And only items imported within the from/to range (inclusive)
And these combine (AND) with the query and type/format filters
```

## AC-5: Search is a scope that coexists with folders
```gherkin
Given a folder filter is active
When the user runs a search (query or any filter)
Then the grid shows search results across the whole library (folder filter cleared)
And selecting a folder afterward clears the search and returns to the folder's items
And with no query and no active filters, the view falls back to folder/all-items as before
```

## AC-6: search IPC is validated and safe
```gherkin
Given the renderer calls items:search
When the query contains SQL/LIKE wildcards (%, _) or quotes
Then they are treated as literal text (bound params; % and _ escaped) — no injection, no accidental match-all
And when no library is open
Then it returns an empty list without throwing across IPC
```

    Create `src/main/services/search.ts` (guard on isDatabaseOpen → []). Define:
      `export interface SearchCriteria {
         query?: string
         types?: ItemType[]      // OR'd among themselves (import ItemType from services/items via its re-export, or from './import')
         ext?: string            // exact format match, lowercased
         minRating?: number      // rating >= this
         from?: number | null    // imported_at >= from (ms epoch)
         to?: number | null      // imported_at <= to (ms epoch)
       }`
    `export function searchItems(criteria: SearchCriteria): Item[]` — build a parameterized
    WHERE from the provided fields (omit absent ones), using POSITIONAL `?` params and a values
    array (mirrors items.ts style; lets the type IN-list expand dynamically):
      - query (trimmed, non-empty): escape LIKE specials in the term — replace `\`,`%`,`_` →
        `\\`,`\%`,`\_` — wrap as `%term%`, and add condition
        `(name LIKE ? ESCAPE '\' OR note LIKE ? ESCAPE '\' OR id IN
          (SELECT it.item_id FROM item_tags it JOIN tags t ON t.id = it.tag_id
           WHERE t.name LIKE ? ESCAPE '\'))` pushing the same pattern 3×.
      - types (non-empty): `type IN (?,?,…)` pushing each type.
      - ext (trimmed non-empty): `ext = ?` pushing ext.toLowerCase().
      - minRating (> 0): `rating >= ?`.
      - from != null: `imported_at >= ?`;  to != null: `imported_at <= ?`.
    Compose `WHERE <conds joined by AND>` (or no WHERE when none), SELECT the SAME columns +
    `ORDER BY imported_at DESC` as items.listItems, and return Item[]. With an all-empty
    criteria, return all items (no WHERE) — equivalent to listItems.
    Register `items:search` in `src/main/ipc/items.ts` → (criteria) searchItems(criteria)
    (import searchItems + SearchCriteria from ../services/search). Do NOT add a new register
    function — items IPC is already wired in index.ts.
    Extend preload `window.api.items` with `search: (criteria) => invoke('items:search', criteria)`
    and add `SearchCriteria` + `search` to the `items` block of `IpcApi` in preload/types.ts.
    Avoid: string-interpolating any value into SQL (bind everything); forgetting ESCAPE so a
    literal % matches all; touching schema.sql / items_fts (explicitly out of scope).
  </action>
