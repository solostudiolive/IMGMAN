<objective>
## Goal
Add **color search**: filter the grid to items whose extracted palette contains a color near a
user-picked color, with an adjustable tolerance. Implemented as a new field on the EXISTING
`SearchCriteria` (a nearest-color post-filter over the stored `items.palette`), surfaced as a color
control in the SearchBar filters popover.

## Purpose
08-02 extracted and stored a dominant-color palette per image (`items.palette` = `#rrggbb` JSON,
most-dominant first). Color search is the payoff — "find everything blue/red/etc." — and a core Eagle
parity feature. Because color is just another `SearchCriteria` field, it flows through the existing
`items:search` IPC and the LibraryGate search scope, and persists into saved searches (08-01) for free.

## Output
- `SearchCriteria` gains `color?: string` (a `#rrggbb` target) and `colorTolerance?: number` (RGB
  Euclidean distance; service supplies a default), mirrored in both `services/search.ts` and
  `preload/types.ts`.
- `searchItems` nearest-color post-filter: when `color` is set, keep an item only if some palette color
  is within tolerance of the target (NULL/empty palettes never match).
- SearchBar filters popover gets a color picker + tolerance select + clear; `isSearchActive`
  (LibraryGate) and the SearchBar active/advanced-count logic recognize `color`.
</objective>

  <name>Task 1: Add color to SearchCriteria + nearest-color post-filter in searchItems</name>

  <action>
    services/search.ts:
    - Extend `SearchCriteria` with:
        `color?: string`           // target dominant color as `#rrggbb` (lowercased)
        `colorTolerance?: number`  // max RGB Euclidean distance to a palette color; default applied below
    - Add a small module-level default + helpers (no deps):
        `const DEFAULT_COLOR_TOLERANCE = 60` (RGB Euclidean distance; mid "close" match).
        `function parseHex(hex): {r,g,b} | null` — accepts `#rgb`/`#rrggbb` (case-insensitive); null on bad input.
        `function paletteMatchesColor(paletteJson: string | null, target: {r,g,b}, tol: number): boolean`
          — JSON.parse in try/catch; if not a non-empty array → false; for each entry parseHex and compute
          squared distance `dr*dr+dg*dg+db*db`; return true as soon as one is ≤ `tol*tol`. Any parse error → false.
    - In `searchItems`: keep the existing WHERE/params build UNCHANGED. Detect `const target = criteria.color
      ? parseHex(criteria.color) : null`. 
        * If `target` is null (no/!invalid color) → run the EXACT current query + projection (no behavior change).
        * If `target` is set → SELECT the same projection PLUS `palette`, run the query, then JS-filter rows
          with `paletteMatchesColor(row.palette, target, criteria.colorTolerance ?? DEFAULT_COLOR_TOLERANCE)`,
          and strip the `palette` field so the return type stays `Item[]`. Ordering (imported_at DESC) is
          preserved because we filter the already-ordered list.
      Implementation note: build the SELECT column list in a variable so the only difference is appending
      `, palette` when color-filtering; do not duplicate the whole function.

    preload/types.ts:
    - Mirror the two new fields on the renderer-facing `SearchCriteria` (same names + the same comment style
      as the existing fields). No IpcApi change (items:search already forwards the whole criteria object).

    Avoid: a new IPC channel; SQL color math / custom SQLite functions (do it in JS); touching the existing
    conds when no color is set; any schema change.
  </action>
