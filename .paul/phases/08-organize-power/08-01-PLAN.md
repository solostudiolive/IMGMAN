<objective>
## Goal
Add **saved searches / smart folders**: persist the current search+filter state (`SearchCriteria`)
under a name, list saved searches in the left sidebar, and re-run one with a click — the grid shows
its results exactly as a live search would. Plus rename and delete.

## Purpose
First of the Phase-8 "organize power features". It reuses the Phase-4 `items:search` path and the
`SearchCriteria` shape verbatim (no new query engine), establishing a per-library persistence pattern
for the heavier Phase-8 features (color search, duplicates) that follow. Lets users keep recurring
views ("5★ PNGs", "videos imported this week") one click away.

## Output
- New `smartFolders:*` IPC (list / create / rename / delete) over the EXISTING `smart_folders` table
  (id, name, rules) — `rules` stores the `SearchCriteria` as JSON. Service → ipc → preload → IpcApi,
  mirroring the `folders:*` triad. No schema change.
- `SmartFolders` sidebar section (presentational, mirrors FolderTree): rows that apply their criteria
  on click, an active highlight, inline rename, and a right-click Rename/Delete context menu.
- A "Save search" affordance in `SearchBar` (shown when a search is active) + LibraryGate wiring that
  owns the smart-folders list, saves the current criteria, and applies a saved one via the existing
  `applySearch` (mutually exclusive with the folder scope).
</objective>

## Patterns to follow
- Backend mirrors `folders:*`: each mutation returns the canonical post-write `SmartFolder[]`; guard
  `isDatabaseOpen()` → []; ids via `crypto.randomUUID()`; order by `name COLLATE NOCASE`.
- `rules` column holds `JSON.stringify(criteria)`; reads `JSON.parse` defensively (parse failure →
  `{}` so a bad row never crashes the list).
- Renderer reconciles to the returned list (like FolderTree's `commit`). Selecting a smart folder
  routes through the EXISTING `applySearch(criteria)` (which already clears the folder scope), so the
  two scopes stay mutually exclusive with zero new scope logic.
- Token styling only (`var(--color-*)`); Electron has no `window.prompt` — use an inline text input
  for naming (mirror FolderTree's add/rename inputs).

<acceptance_criteria>

## AC-1: Save the current search as a smart folder
```gherkin
Given an active search/filter (e.g. query "logo" + type=image + 4★)
When the user clicks "Save search" and types a name
Then smartFolders:create stores it (name + the criteria JSON) and it appears in the sidebar
  "Smart Folders" section
And the "Save search" control is hidden when no search is active
```

## AC-2: Apply a saved search
```gherkin
Given one or more saved smart folders exist
When the user clicks a smart folder row
Then its SearchCriteria is applied via the existing search scope and the grid shows those results
And the active folder selection is cleared (search and folder scopes stay mutually exclusive)
And the clicked smart folder shows an active highlight
```

## AC-3: Rename and delete
```gherkin
Given a saved smart folder
When the user renames it (inline or via the right-click menu)
Then smartFolders:rename persists the new name and the list reflects it
When the user deletes it (with confirm)
Then smartFolders:delete removes it and the row disappears; items and search state are untouched
```

## AC-4: Per-library persistence
```gherkin
Given smart folders saved in library A
When the app reloads or switches to library A
Then the saved smart folders load from that library's DB and render in the sidebar
And switching to a different library shows that library's own smart folders (not A's)
```

## AC-5: No regressions
```gherkin
When `npm run typecheck` (node + web) and `npm run build` run
Then both pass with no new errors
And schema.sql is unchanged (reuses the existing smart_folders table)
And live search, the folder filter, and all Phase 7 selection/batch features are unaffected
```
