<objective>
## Goal
Add a standalone "Import from URL" feature: the user enters a URL in a modal dialog, the app fetches
the content through a hardened main-process pipeline (security validation → fetch → stream → thumbnail),
and imports it through the SAME path as dropped files (copy original + thumbnail + palette + hash +
metadata row with `source_url` populated).

## Purpose
Completes the v1.1 "Rich Media Import" feature set. URL import is the standalone path the user
requested (reuses the Phase-2 import core; the browser extension stays deferred). The `source_url`
column already exists in schema.sql (line 169) and `items.update` already supports it — URL import
just needs to populate that field at import time.

## Decision: Main-process fetch with defense-in-depth validation
All network I/O runs in the main process (never the sandboxed renderer). The renderer only passes the
URL string to a typed IPC call. The main-process `importUrl(url)` service layer:
1. **Validates** the URL (parseable, http/https scheme, NOT loopback, NOT private ranges, NOT `file:`)
2. **Fetches** with a redirect cap (≤5) and a size cap (configurable, default 50 MB)
3. **Classifies** by extension (reuses `classifyType` from import.ts) — non-allow-listed types rejected
4. **Streams** the response body to `images/<id>/original.<ext>` (never loads full body in memory)
5. **Extracts** thumbnail + palette + hash via the EXISTING Phase-10 media thumbnail extractors
6. **Inserts** the row with `source_url` set to the original URL

Security: the loopback/private-range block is the critical guard — it prevents SSRF-style attacks
where a malicious page could make the local app fetch `http://127.0.0.1:5432/` or internal
admin panels. The allow-list of file types prevents arbitrary binary storage.
</objective>

## AC-1: URL validation blocks unsafe targets
```gherkin
Given a URL entered by the user
When the URL is `http://127.0.0.1/`, `http://localhost:8080/`, `file:///etc/passwd`, or within a private IP range (10.x / 172.16-31.x / 192.168.x)
Then the import is rejected with a clear error message
And no network request is made
```

## AC-2: URL import produces real item in the library
```gherkin
Given a valid URL to an image file (e.g., https://example.com/photo.jpg)
When the user submits the URL in the Import from URL dialog
Then the content is fetched and imported through the same pipeline as dropped files
And a library item is created with source_url set to the original URL
And a real thumbnail.webp is generated
And width/height/palette/content_hash are populated
And the grid shows the new item immediately
```

## AC-3: Size cap prevents runaway downloads
```gherkin
Given a URL pointing to a file larger than the configured max size (default 50 MB)
When the user submits the URL
Then the fetch is aborted
And the import fails with a clear "file too large" error
And no partial file is stored
```

## AC-4: Non-allow-listed types are rejected
```gherkin
Given a URL pointing to an HTML page or executable (e.g., .exe, .html, .sh)
When the user submits the URL
Then the import is rejected based on the file-type allow-list
And a clear error is shown
```

## AC-5: Graceful error handling
```gherkin
Given a URL that is unreachable, returns 404, or times out
When the user submits the URL
Then a clear error message is shown in the dialog
And no partial/corrupt item is created in the library
```

## AC-6: Progress feedback during fetch
```gherkin
Given a URL to a large media file (e.g., 20 MB video)
When the user submits the URL
Then a progress indicator shows download progress
And the dialog is non-blocking (user can cancel via Escape)
```
